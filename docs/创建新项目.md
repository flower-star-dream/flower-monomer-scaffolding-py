# 从脚手架创建新项目 / 升级项目

> @Author: 花海
> @Date: 2026/08/16
> @Description: 从 flower-monomer-scaffolding 脚手架派生业务项目的两种方式（推荐 Use this template / 手动 clone）、
>               已生成项目升级（upgrade）、版本发布快照（snapshot），及内置脚本 scripts/new_project.py 的参数说明与常见问题。

## 1. 两种方式总览

| 方式                                                             | 适用场景                           | 关键点                                           |
| ---------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------ |
| [方式一：Use this template（推荐）](#方式一use-this-template推荐) | 新项目将在 GitHub 上托管           | GitHub 原生生成全新 git 历史，不继承脚手架提交   |
| [方式二：手动 clone 脚手架](#方式二手动-clone-脚手架)             | 本地离线生成 / 仓库未开启 Template | `rm -rf .git` + `git init` 获得全新 git 历史 |

无论哪种方式，拿到脚手架代码后统一运行内置脚本 `scripts/new_project.py` 完成项目名 / 包名 / 数据库名 / 作者 / 版本的重命名，并在项目根写入 `.scaffold-info.json`（升级依据）。已生成项目后续可通过 `upgrade` 命令同步新版脚手架（见 [6. 项目升级与版本发布](#6-项目升级与版本发布)）。

## 2. 前置条件

- Python >= 3.10、git。

## 3. 方式一：Use this template（推荐）

```bash
# 1) GitHub 上打开脚手架仓库，点击 "Use this template"，填写新仓库名创建（GitHub 生成全新 git 历史）
# 2) clone 新仓库到本地
git clone https://github.com/<org>/<new-repo>.git
cd <new-repo>

# 3) 运行重命名脚本（默认原地重命名，自动删除 scripts/ 自身目录）
python scripts/new_project.py new my-project

# 4) 按输出提示安装依赖、配置 .env、启动
python -m venv .venv && .venv\Scripts\activate
pip install "flower-web-infrastructure[mysql,redis,migrate] @ git+https://github.com/flower-star-dream/flower-web-infrastructure.git"
pip install -e ".[dev]"
cp .env.example .env        # 填写敏感配置
uvicorn my_project.main:app --host 0.0.0.0 --port 8000 --reload
```

> 说明：`.github/workflows/ci.yml` 中 GHCR 推送地址使用 `github.repository` 自动跟随新仓库，无需修改；首次推送后需在 GitHub `Settings → Packages` 设置镜像包可见性。

## 4. 方式二：手动 clone 脚手架

```bash
# 1) 拉取脚手架代码
git clone https://github.com/flower-star-dream/flower-monomer-scaffolding-py.git my-project
cd my-project

# 2) 关键：删除脚手架 git 历史，初始化全新仓库（否则新项目会继承脚手架全部提交）
rm -rf .git
git init

# 3) 重命名 + 首次提交
python scripts/new_project.py new my-project
git add . && git commit -m "chore: 从脚手架初始化 my-project"
```

> 也可在 GitHub 上 fork 脚手架后 clone 到本地，再按 2) 删除 `.git` 初始化新仓库（fork 的 PR 提交流程与本地独立仓库互不影响）。

## 5. 脚本用法

```bash
python scripts/new_project.py new <project-name> [options]        # 生成新项目
python scripts/new_project.py upgrade <project-dir> [options]     # 升级已生成项目
python scripts/new_project.py snapshot <version>                  # 生成模板快照基线（发版）
python scripts/new_project.py --help
```

### 5.1 new 参数

| 参数                  | 必填 | 默认                  | 说明                                                                         |
| --------------------- | ---- | --------------------- | ---------------------------------------------------------------------------- |
| `project-name`      | 是   | —                    | 新项目名（如`my-project`），用于 pyproject / README / 镜像名 / GHCR 仓库名 |
| `--package`         | 否   | 项目名转 snake_case   | Python 包名（`src/<package>`，如 `my-project` → `my_project`）        |
| `--db mysql\|sqlite` | 否   | 随组件选择（默认 mysql） | 数据库类型快捷参数（等价于 `--components=db:<type>`）                  |
| `--db-name`         | 否   | 项目名转 snake_case   | 数据库名（替换`flower_monomer`）                                           |
| `--components`      | 否   | 交互式询问 / 最小化默认 | 组件与实现选择（`name:impl` 逗号分隔，如 `cache:redis,mq:rocketmq`；`all`=全部默认 / `none`=仅必选组件；未提及的可选组件默认不使用；注册中心禁止内存实现） |
| `--org`             | 否   | `flower-star-dream` | GitHub 组织名（替换 README 徽章链接）                                        |
| `--version`         | 否   | `0.1.0`             | 初始版本号                                                                   |
| `--author`          | 否   | 不替换                | 作者名（替换全部`@Author: 花海` 与 pyproject authors）                     |
| `--dir`             | 否   | 当前目录              | 目标输出目录（提供则复制生成，模板目录保持不动；缺省原地重命名）             |
| `--git-init`        | 否   | false                 | 自动`git init` + 首次提交（手动 clone 方式可配合使用）                     |

### 5.2 upgrade 参数

| 参数                  | 必填 | 默认            | 说明                                                       |
| --------------------- | ---- | --------------- | ---------------------------------------------------------- |
| `project-dir`       | 是   | —              | 目标业务项目根目录（含`.scaffold-info.json`）            |
| `--to`              | 否   | 当前模板版本    | 目标脚手架版本（`x.y.z`）                                |
| `--framework-version` | 否 | 不更新          | 目标框架版本（如`0.2.0`），更新`framework_pin`并输出升级命令 |
| `--dry-run`         | 否   | false           | 只预览变更，不写盘                                         |

### 5.3 snapshot 参数

| 参数                  | 必填 | 默认 | 说明                                                   |
| --------------------- | ---- | ---- | ------------------------------------------------------ |
| `version`           | 是   | —    | 版本号（`x.y.z`，生成到`scaffold/versions/v<version>/`） |

### 5.4 重命名范围

脚本自动完成以下替换（顺序：先长串后短串，运行时属性先保护后恢复）：

- 项目名 `flower-monomer-scaffolding` → `<project-name>`（pyproject / application.yml / .env.example / ci.yml 镜像标签 / docs）；
- 仓库名 `flower-monomer-scaffolding-py` → `<project-name>`（README 徽章 / GHCR 地址）；
- 数据库名 `flower_monomer` → `<db-name>`（.env.example / application.yml 默认值 / alembic 错误提示 / db/init SQL）；
- Python 包 `src/app` → `src/<package>`，`from app.` / `import app.` / `uvicorn app.main:app` → `<package>` 对应写法；
  - **运行时实例属性保留**：`app.state` / `app.include_router` / `app.routes` / `app.url_path_for`（FastAPI 实例访问，非包名）不被替换；
- 版本号 `0.1.0` → `<version>`（--version）；
- 作者 `@Author: 花海` → `@Author: <author>`（--author）。

同时：覆盖 `README.md` 为新项目初始化版；按组件选择裁剪 `application.yml` / `.env.example` 配置段（未选组件整块移除、已选组件按实现替换 type/enabled）；选择自研（custom）的组件在 `src/<package>/spi/` 生成实现骨架；删除脚手架专属内容（`scripts/`、CLI 测试、设计文档、`*.egg-info` 构建产物）；写入 `.scaffold-info.json`（含组件选择记录）。

### 5.5 组件与实现选择

`new` 支持按框架全部能力组件选择生成：**组件（使用什么）→ 实现（启用哪个实现）→ SPI 策略（默认 / 生产实现 / 自行实现）**，覆盖框架全部能力组件：

| 分组 | 组件 | 可选实现 | 默认 |
| ---- | ---- | -------- | ---- |
| 基础设施 | 数据库 db | mysql / sqlite / orm_custom（基于框架 ORM 自定义）/ custom（完全自定义） | mysql |
| 基础设施 | 缓存 cache | 不使用 / memory(默认) / redis / custom | memory |
| 基础设施 | 对象存储 storage | 不使用 / local(默认) / minio / custom | local |
| 基础设施 | 消息队列 mq | 不使用 / memory(默认) / rocketmq / custom | memory |
| 基础设施 | 注册中心 registry | 不使用 / nacos / custom（**禁止内存实现**） | 不使用 |
| 基础设施 | 配置中心 config | 不使用 / nacos / custom | 不使用 |
| 基础设施 | MongoDB mongo | 不使用 / 启用 | 不使用 |
| 业务能力 | 支付 payment | 不使用 / memory(默认) / wechat / custom | memory |
| 业务能力 | AI 能力 ai | 不使用 / 默认装配 / custom | 不使用 |
| 业务能力 | 安全组件 security | 不使用 / memory(默认) / redis / custom | memory |
| 业务能力 | JWT 鉴权 jwt | 不使用 / 默认策略 / redis / custom | 默认策略 |
| 业务能力 | 三方登录 social | 不使用 / demo(默认) / custom | demo |
| 业务能力 | 异步任务 task | 不使用 / memory(默认) / custom | memory |
| 平台质量 | 任务调度 schedule | 不使用 / 启用 | 不使用 |
| 平台质量 | 状态机 state_machine | 不使用 / 启用 | 不使用 |
| 平台质量 | 监控 monitoring | 不使用 / 启用 | 启用 |
| 平台质量 | 多租户 tenant | 不使用 / 启用(strict) | 不使用 |
| 平台质量 | 幂等中间件 idempotency | 不使用 / memory(默认) / redis / custom | 不使用 |

交互式询问（TTY 下缺省 `--components` 时逐个提问，回车取最小化默认：可选组件默认不使用）；非交互环境（CI / 脚本）默认最小化（仅必选 db），用参数显式指定所需组件：

```bash
# 显式指定组件与实现（未指定的可选组件默认不使用，避免配置全量给出）
python scripts/new_project.py new my-project --components=db:sqlite,cache:redis,mq:rocketmq,registry:nacos,payment:wechat,idempotency:redis

# all=全部默认 / none=仅必选组件（db）
python scripts/new_project.py new my-project --components=all
python scripts/new_project.py new my-project --components=none
```

规则与效果：

- **注册中心禁止内存实现**：`registry` 仅可选 不使用 / nacos / custom（内存只用于单体/测试的单进程场景，脚手架按要求一律不提供该选项）；
- **未选组件整块移除**：`application.yml` / `.env.example` 中未选择或关闭的组件配置段（`# <<<COMPONENT:<name>>>` 标记块）整体移除，生成项目只含所选组件配置；
- **已选组件按实现替换**：模板块内为合法默认值（脚手架自身可直接运行），生成时按选择替换 `type`（如 cache memory→redis）或翻转 `enabled`（如 ai/mongo 默认关闭，选择后启用）；
- **SPI 默认策略 vs 自行实现**：每个组件可选策略型实现（`custom` / `orm_custom` 等），选择后生成 `src/<package>/spi/<组件>_<实现>.py` 实现骨架（类 + 方法签名 + TODO 提示），由你补全后接入装配；默认实现（内存）与生产实现（Redis/MinIO/RocketMQ/Nacos/微信）均无需写代码。数据库组件区分两类自研：
  - `db=orm_custom`：**基于框架已有 ORM 自定义**——复用 SQLAlchemy 生态（SqlAlchemyDatabaseSession / MySQLDatabase / DatabaseManager），按需自定义数据源、会话行为或动态路由（DatabaseRouterInterface），生成 `db_orm_custom.py`；
  - `db=custom`：**完全自定义**——自行实现 DatabaseSessionInterface / DatabaseFactoryInterface（如接入 PostgreSQL / 其他 ORM / 其他数据源），生成 `db_custom.py`；
  - 两类均保留 `application.yml` 的 `db.type` 默认值（不写非法 type），框架装配回落 MySQL 默认，接入骨架后由你在装配处替换；
- **README 与安装命令联动**：生成 README 的「启用的组件」表与框架安装 extras 按选择渲染（如 cache=redis → `[redis]`）；选择记录写入 `.scaffold-info.json`，`upgrade` 沿用。自研骨架生成在 `src/<package>/spi/`（生成后仍可按需增删组件配置，框架对未配置组件回落内置默认实现）；
- **能力依赖装配（框架 2026-08-17）**：`application.yml` 的 `app.capabilities.enabled` 由组件选择自动生成（如选择支付 → `"pay"`、JWT/三方登录/安全 → `"authn"`、消息队列 → `"mq"`），装配时框架按依赖包含关系自动补足前置（`pay` 自动带上 `authz → authn → user`）；支付为可选能力，不随 `web_infra` 顶层导出，业务代码用 `from web_infra.payment import ...` 显式导入（脚手架示例已如此）。

## 6. 项目升级与版本发布

### 6.1 项目升级（upgrade）

将已生成项目同步到新版脚手架，采用**三路合并**（diff+patch）：`base`（旧版模板快照）+ `ours`（项目现状）+ `theirs`（新版模板），仅同步脚手架固有文件，**业务改动冲突时报告而不覆盖**。

```bash
# 在脚手架仓库内执行（默认升到当前模板版本；--dry-run 只预览不写盘）
python scripts/new_project.py upgrade /path/to/my-project [--to 0.2.0] [--framework-version 0.2.0] [--dry-run] [--components ...]
```

前置条件：

- 项目由 `new` 命令生成，且根目录保留了 `.scaffold-info.json`；
- 脚手架仓库已存在项目对应旧版本的模板快照 `scaffold/versions/v<旧版本>/`（见 [6.2 版本发布与快照](#62-版本发布与快照snapshot)）；
- 升级前建议先 `git commit` 当前改动，便于冲突后回溯。

三路合并规则：

| base 旧模板 | ours 项目现状 | theirs 新模板 | 动作 |
| ----------- | ------------- | ------------- | ---- |
| 不变 | 任意 | 不变 | 跳过（不触碰） |
| 已变 | == base（业务未改） | 已变 | 更新为新版模板 |
| 已变 | != base 且 != theirs（业务也改了） | 已变 | **冲突**：报告，不覆盖 |
| 无此文件 | 无此文件 | 新增 | 新增补齐 |
| 有 | 已删除 | 有 | 缺失：报告（业务删除了模板文件，需人工确认） |
| 有 | == base | 已废弃 | 删除该文件 |
| 有 | != base（业务改了） | 已废弃 | **冲突**：报告，不覆盖 |

- **README.md** 为业务文件，不参与自动同步（`new` 时已被覆盖），升级后请手工比对；
- 冲突清单在输出中列出，需手工合并后提交；
- 组件选择沿用项目 `.scaffold-info.json` 记录（旧版项目无记录时按 `db_type` 派生），`--components` 可覆盖（同时更新记录）；
- `--db sqlite` 生成的项目，升级时 `application.yml` 的 `type: sqlite` 会被保留（模板默认 mysql，自动按记录参数转换）。

框架版本升级：`--framework-version <ver>` 提供时更新 `.scaffold-info.json` 的 `framework_pin` 并输出升级命令：

```bash
pip install "flower-web-infrastructure[mysql,redis,migrate] @ git+https://github.com/flower-star-dream/flower-web-infrastructure.git@v0.2.0"
```

### 6.2 版本发布与快照（snapshot）

脚手架每次发布新版本时生成**模板基线快照**，供 upgrade 作为旧版对照（三路合并的 base）：

```bash
# 1) 在脚手架仓库内更新 scripts/new_project.py 的 TEMPLATE_VERSION 为新版本号
# 2) 生成快照（拷贝当前模板，排除脚手架专属内容）
python scripts/new_project.py snapshot 0.2.0
# 3) 提交 scaffold/versions/v0.2.0/ 与脚本变更，可选打 git tag v0.2.0
```

- 快照保存在 `scaffold/versions/v<版本>/`，保留模板原始标识（未替换）；
- `new` 派生新项目时快照目录不复制进业务项目（属于脚手架专属内容）。

## 7. 常见问题

- **改了脚手架代码，但 git 历史仍属于脚手架**：删除 `.git` 后 `git init`（见方式二第 2 步），或改用方式一重新生成。
- **要不要把脚手架后续更新同步到新项目**：视情况而定。脚手架新增的**脚手架固有文件**（配置 / CI / Dockerfile / 文档骨架等）可通过 `upgrade` 命令同步（见 [6.1 项目升级](#61-项目升级upgrade)）；业务代码请自行演进，模板不会覆盖已改动的文件。
- **upgrade 报"缺少旧版模板基线"**：项目记录的 `scaffold_version` 对应的 `scaffold/versions/v<版本>/` 不存在。原因通常是脚手架仓库未同步到该版本（含快照目录），`git pull` 或切换分支后重试；旧项目若从未生成过快照，需手工升级。
- **生成后测试报 `ModuleNotFoundError: web_infra`**：框架依赖未安装，执行 `pip install "flower-web-infrastructure[mysql,redis,migrate] @ git+https://github.com/flower-star-dream/flower-web-infrastructure.git"`。
- **CI 推送镜像失败（403 / denied）**：首次推送后在 GitHub `Settings → Packages` 设置新仓库镜像包可见性并授权成员。
